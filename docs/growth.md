> 발표 준비·대본 작성용 참고 문서

## 3. 사용자 확장 전략 — B2C → B2B

### 3-1. B2C: 학생 시장 (현재)

- **타깃**: 녹음 강의·PDF 자료를 동시에 다루는 대학생
- **핵심 가치**: 수작업 노트 정리 → AI 자동화로 주당 3~5시간 절약
- **유입 채널**: 대학 커뮤니티(에브리타임, 학과 오픈채팅), 유튜브 "공부법" 채널

### 3-2. B2B: 회의·문서 요약 (1차 확장, 가장 빠른 시장)

**이 제품의 본질은 강의 요약이 아니다. 비정형 멀티모달 입력 → 구조화 출력 파이프라인이다.**  
동일한 파이프라인이 비즈니스 환경에서 더 큰 수요를 가진다.

| 사용 시나리오 | 입력 | Step 0 컨텍스트 | 출력 |
|---|---|---|---|
| **회의 요약** | 녹음 파일 + 회의 자료 PDF | 안건 목록 / 조직도 | 결정 사항·액션 아이템·참석자별 책임 |
| **문서 요약** | 계약서·보고서 PDF (다수) | 검토 체크리스트 | 핵심 조항·리스크 항목·요약표 |
| **사내 온보딩** | 신입 교육 녹음 + 정책 문서 | 온보딩 가이드 | 부서별 핵심 내용·FAQ |
| **세미나·컨퍼런스** | 발표 녹음 + 슬라이드 PDF | 행사 프로그램 | 세션별 요약 + 네트워킹 인사이트 |

**전환 포인트**: 코드를 바꾸지 않는다. Step 0 컨텍스트 문서(강의계획서 → 안건 목록 → 검토 체크리스트)만 교체하면 된다.

**시장 크기 비교**:
- 대학생 강의 노트: B2C, ARPU 낮음, 계절성 있음
- 기업 회의·문서 요약: B2B, ARPU 높음, 연중 발생, 반복 구독 가능성 높음

### 3-3. B2B: 전문직 도메인 (장기)

| 도메인 | Step 0 컨텍스트 교체 | 출력물 |
|---|---|---|
| 감사·실사 | 감사 체크리스트 | 리스크 항목 정리 보고서 |
| 컨설팅 | 과제 정의서 | 구조화된 분석 초안 |
| 법무·컴플라이언스 | 규정·체크리스트 | 검토 요약 및 위험 플래그 |
| 의료·임상 | 진료 가이드라인 | 진찰 기록 구조화 |
| 투자·IR | 투자 체크리스트 | 리스크·기회 요인 요약 |

> **핵심 메시지**: 제품을 바꾸는 것이 아니라 Step 0 컨텍스트만 교체하면 된다. 파이프라인 아키텍처가 도메인 독립적으로 설계된 이유가 여기에 있다.

## 4. 기술 로드맵

### Phase 1 — 검증 단계 (현재)

**목표**: 핵심 파이프라인이 실제로 가치를 제공하는지 검증

| 스택 | 선택 | 이유 |
|---|---|---|
| DB | SQLite | 인프라 의존성 없이 빠른 검증 |
| 서버 | 단일 FastAPI | 배포·운영 복잡도 최소화 |
| 배포 | Railway | 안정적인 외부 접근 URL |
| 모바일 | PWABuilder TWA + Capacitor | APK/AAB 빌드 완료, Play Store 등록 준비 |

**한계**: 컨테이너 재시작 시 데이터 소실 위험 (Persistent Volume 미설정), 동시 요청 처리 제한

---

### Phase 2 — 안정화 단계 (사용자 발생 이후)

**트리거**: 실사용자 발생, 데이터 보존 필요성 확인

| 항목 | 변경 | 비고 |
|---|---|---|
| DB | SQLite → **PostgreSQL** | Supabase 무료 티어 또는 Railway Postgres |
| 스토리지 | 로컬 → **S3 호환** (Cloudflare R2) | 업로드 파일 영구 보존 |
| 인증 | SHA256+salt → **bcrypt** | 보안 강화 |
| 비밀번호 찾기 | 데모 메시지 → **실제 이메일 발송** | SendGrid / AWS SES |
| 배포 | Railway 무료 → **유료 플랜** | 안정적 상시 가동 |
| 모바일 | TWA → **네이티브 기능 강화** | Capacitor 플러그인 확장 |

---

### Phase 3 — 확장 단계 (B2B 진입 이후)

**트리거**: 동시 사용자 수십 명 이상, 긴 처리 시간 불만 발생

| 항목 | 변경 | 이유 |
|---|---|---|
| 파이프라인 처리 | 동기 → **비동기 큐** (Celery + Redis) | LLM 응답 대기 중 서버 블로킹 해소 |
| STT | Gemini Audio → **전용 STT 서비스** (Whisper API 등) | 처리 속도 및 정확도 향상 |
| LLM | Gemini 2.5-flash → **모델 선택 가능** (GPT-4o, Claude 등) | Pro 사용자 고품질 옵션 제공 |
| 서버 | 단일 서버 → **서비스 분리** | STT 서비스 / LLM 서비스 독립 스케일링 |
| 멀티테넌시 | 사용자별 격리 → **조직(Org) 단위 격리** | Team 플랜 완전 지원 |

## 5. 기능 확장 로드맵

| 기능 | 설명 | 우선순위 |
|---|---|---|
| **다중 파일 업로드** | PDF·음성 파일 여러 개 동시 인제스천, 백엔드 병렬 처리 확장 | **단기** |
| **노트에 대한 추가 요청** | 생성된 노트를 기반으로 후속 질의 ("이 부분 더 자세히 설명해줘", "예상 문제 5개 더 만들어줘") | **단기** |
| 이미지 입력 | Gemini Vision으로 칠판 사진·필기 이미지 처리 | 중기 |
| 처리 메타데이터 표시 | 소스 구성·처리 시간·토큰 사용량 표시 | 단기 |
| Play Store 배포 | PWABuilder AAB → Google Play 등록 (빌드 완료, 등록 절차 진행 필요) | 단기 |
| 노트 공유 링크 | 읽기 전용 공개 URL 생성 | Pro 기능 |
| 팀 공유 워크스페이스 | 조직 내 노트 공동 열람, 코멘트 | Team 기능 |
| 전체 노트 키워드 검색 | 백엔드 Full-Text Search (SQLite FTS5 / PostgreSQL tsvector) | 중기 |
| 다국어 노트 출력 | 한국어 외 영어·일본어 출력 선택 | 장기 |

### 다중 파일 업로드 구현 방향

현재 `generate-note` 엔드포인트는 파일 1개씩 받는다. 확장 시:
- 프론트: 파일 선택 UI → 다중 선택 (`multiple` 속성) + 선택 파일 목록 표시
- 백엔드: `pdf_file: List[UploadFile]`, `audio_file: List[UploadFile]` 타입 변경
- 처리: `asyncio.gather`로 병렬 파싱 후 `aggregator`에서 소스 병합

### 노트 추가 요청 구현 방향

노트 조회 화면에 대화창 추가 — 생성된 노트 내용을 컨텍스트로 포함해 Gemini에 후속 요청 전송.
- 새 엔드포인트: `POST /api/notes/{id}/ask` — `{question: str}` 수신, SSE 스트리밍 응답
- 컨텍스트: 기존 노트 요약 + Step 0 커리큘럼 + 사용자 질문
- 사용 예: "3번 섹션 더 자세히", "이 내용으로 플래시카드 만들어줘", "예상 문제 3개 더"

## 6. 경쟁 포지셔닝

| 서비스 | 강점 | LectureNote 대비 차별점 |
|---|---|---|
| Notion AI | 범용 문서 작업 | LectureNote는 멀티모달 인제스천 + 도메인 컨텍스트 주입에 특화 |
| Otter.ai | STT 전문 | STT를 넘어 PDF·필기 통합 및 구조화 노트 생성까지 처리 |
| ChatGPT | 범용 LLM | Step 0 커리큘럼 분석을 매 요청에 자동 주입하는 파이프라인 구조 없음 |
| 클로바노트 | 한국어 STT·회의록 | 강의계획서 기반 컨텍스트 주입 및 시험 대비 구조화 출력 없음 |

**핵심 차별점**: 단순 요약이 아니라 **사전 분석된 구조적 컨텍스트(Step 0)를 매 생성 요청에 주입**하는 설계. 이는 RAG의 simplified version과 동일한 원리로, 도메인 인식 생성(context-conditioned generation)을 가능하게 한다.

## 7. 발표·면접 활용 포인트

### "왜 유료화가 가능한가?"

> 수작업 노트 정리에 주당 3~5시간을 쓰는 학생에게 월 ₩9,900은 시간 1시간의 가치도 안 된다.  
> 기업 교육팀 입장에서는 신입 온보딩 자료 1건 수작업 비용이 수십만 원 — 팀 플랜 ₩29,900은 그 10분의 1도 안 된다.

### "왜 B2B로 확장 가능한가?"

> 파이프라인의 핵심은 강의 처리가 아니라 **이기종 비정형 입력 → 구조화 출력** 아키텍처다.  
> Step 0 컨텍스트만 교체하면 회의 요약, 문서 검토, 온보딩 가이드, 감사 보고서 등 어떤 도메인에도 적용된다.  
> 강의 노트는 그 파이프라인의 첫 번째 검증 사례일 뿐이다. 코드는 이미 그 구조로 구현되어 있다.

### "강의 요약이 아니라 비즈니스 도구라고 볼 수 있는가?"

> 실제로 회의 녹음 파일 + 안건 PDF를 넣으면 현재 코드가 그대로 동작한다.  
> Step 0에 안건 목록을 넣으면 결정 사항·액션 아이템이 구조화되어 나온다.  
> UI 레이블 몇 개만 바꾸면 회의 요약 SaaS가 된다. 파이프라인 코드는 건드릴 필요가 없다.

### "현재 기술 선택(SQLite, 단일 서버)이 부족하지 않은가?"

> 의도적 선택이다. 검증 전에 PostgreSQL·마이크로서비스를 도입하는 것은 운영 복잡도만 높인다.  
> 실사용자와 트래픽이 생긴 다음 단계적으로 전환하는 것이 엔지니어링 관점에서 올바른 순서다.
