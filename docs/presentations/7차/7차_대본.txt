[슬라이드 2 - 프로젝트 타임라인] (1:30)

본격적인 내용에 앞서, 한 학기 전체 개발 흐름을 타임라인으로 먼저 짚고 넘어가겠습니다.

저희는 1차 발표에서 아이디어 기획과 서비스 방향을 잡았고,
2차에서는 요구사항 분석과 시스템 설계를 마쳤습니다.
3차에 백엔드 MVP를, 4차에 프론트엔드까지 붙인 알파 빌드를,
5차에는 외부 배포까지 완료한 베타 빌드를 완성했습니다.
그리고 6차에서는 실제 외부 사용자 피드백을 반영해 최종 빌드를 완성했습니다.

오늘 7차는 그 최종 완성본을 정식으로 발표하는 자리입니다.

6차 이후로 새롭게 달성한 항목들을 보시면,

또 Google Play 비공개 테스트 등록 신청을 완료해서 현재 구글의 심사가 진행 중입니다.
마지막으로 기존에 Render에서 운영하던 배포 환경을 Railway로 전환해 안정성을 높였습니다.
현재 배포 URL은 화면에 표시된 주소로 바로 접속 가능합니다.


[슬라이드 3 - 문제 정의 + SDLC] (1:30)

저희가 이 서비스를 만들게 된 이유, 즉 해결하려 했던 문제부터 말씀드리겠습니다.

문제는 간단합니다. 저희 팀원들이 직접 겪은 불편함에서 출발했습니다.

대학 강의를 듣다 보면 세 가지 벽에 부딪힙니다.
첫째, 빠른 강의 속도 때문에 필기에 집중하면 내용을 놓치고, 내용에 집중하면 필기를 못 합니다.
둘째, 수업이 끝나면 녹음 파일, 교수님 PPT, 내 손 필기가 전부 따로 흩어져 있어 한 번에 정리하는 게 불가능합니다.
셋째, 이렇게 흩어진 자료들을 통합한 구조화 노트가 없으니
시험 기간마다 처음부터 다시 정리해야 하는 상황이 반복됩니다.

저희 솔루션은 이 세 가지를 한 번에 해결합니다.
"STT, PDF, 필기를 동시에 입력받아 LLM이 구조화 노트를 자동으로 만든다."

개발 방식은 소프트웨어 공학의 SDLC 표준 모델을 따랐습니다.
요구분석, 설계, 구현, 테스트, 배포·운영, 이 다섯 단계를 학기 일정에 맞춰 순서대로 밟아왔고,
현재는 마지막 단계인 배포·운영 단계에 와 있습니다.


[슬라이드 4 - 데이터 파이프라인] (2:00)

그러면 실제로 시스템이 어떻게 동작하는지, 데이터 파이프라인 구조로 설명드리겠습니다.

사용 흐름은 크게 두 단계로 나뉩니다.

첫 번째는 강의 등록입니다. 학기 초에 딱 한 번만 하면 됩니다.
강의계획서 PDF를 업로드하면 Gemini가 이를 분석해서,
해당 강의의 주차별 커리큘럼 구조, 핵심 주제, 교수님의 강조 패턴을 추출합니다.
이것을 저희는 Step 0 로드맵이라고 부르는데, 이 로드맵이 DB에 저장됩니다.

두 번째는 매주 반복하는 노트 생성 단계입니다.
수업이 끝난 뒤 녹음 파일, 수업자료 PDF, 그리고 원하면 개인 필기까지 업로드합니다.
이 세 가지 입력이 들어오면, Gemini가 음성을 텍스트로 변환하고
PDF 파서가 슬라이드 텍스트를 추출합니다.
그리고 앞서 저장해둔 Step 0 로드맵이 강의 맥락으로 함께 주입됩니다.
Data Aggregator가 이 모든 정보를 하나로 묶어 Gemini LLM에 전달하면,
5개 섹션으로 구성된 구조화 노트가 생성됩니다.

5개 섹션은 이번 주차의 강의 위치와 개요, 중요도 별점이 달린 통합 노트,
교수님이 직접 강조한 힌트 모음, 핵심 암기 목록, 그리고 출제 경향 기반 예상 시험 문제입니다.

결과물은 앱 안에서 바로 조회하거나 편집할 수 있고, PDF나 HTML 파일로 다운로드도 됩니다.

가장 중요한 포인트는 이겁니다.
학기 초에 강의계획서를 한 번 등록해두면,
이후 매주 노트를 만들 때마다 교수님의 강의 의도와 출제 경향이 자동으로 반영됩니다.
사용자가 매번 배경 설명을 할 필요가 없습니다.


[슬라이드 5 - STT 전략 변경] (1:30)

개발 과정에서 바뀐 중요한 설계 결정을 한 가지 공유드리겠습니다.

원래 2차 발표 때 저희는 음성 인식에 네이버 CLOVA API를 쓰기로 했었습니다.
그런데 실제 개발이 진행되면서 문제가 생겼습니다.
CLOVA 무료 티어가 소진되어버렸고, 그 순간 저희 서비스의 STT 기능이 실제로 중단됐습니다.
개발 중간에 외부 API 의존도의 위험성을 직접 경험한 겁니다.

이 시점에 구조를 전면 재검토했고, 결론은 Gemini의 멀티모달 기능으로 전환하는 것이었습니다.
음성 파일을 별도의 변환 없이 Gemini에 직접 전달하는 방식입니다.

전환의 장점은 세 가지입니다.

첫째, 비용입니다. LLM 호출과 동일한 API 키 하나로 STT까지 처리되기 때문에
STT 별도 비용 구조 자체가 사라집니다.

둘째, 아키텍처 단순화입니다. 외부 STT API가 사라지면서 장애 지점이 하나 줄었고,
유지보수도 훨씬 단순해졌습니다.

셋째, 향후 전환 가능성입니다.
현재는 프로토타입 단계라 Gemini STT를 사용하지만,
사업화 단계에서는 오픈소스 Whisper를 자체 서버에 배포해서
음성 데이터가 외부로 전혀 나가지 않는 구조로 전환할 계획입니다.
보안과 개인정보 측면에서도 더 강해지는 방향입니다.


[슬라이드 6 - 사용자 피드백] (2:00)

잠시 후 시연 영상을 보여드리겠는데, 그 전에 이 영상에 담긴 최종 빌드가 어떤 과정을 거쳐 만들어졌는지 먼저 설명드리겠습니다.

저희는 5차 베타 빌드를 완성한 뒤, 저희 팀과 전혀 무관한 외부 사용자 5명에게 실제로 써보게 했습니다.
단순 설문이 아니라, 배포 URL로 직접 접속해서 강의 등록부터 노트 생성까지 전 과정을 경험한 뒤 인터뷰를 진행했습니다.

가장 자주 언급된 의견 5가지를 추려보면,

강점으로는 두 가지가 나왔습니다.
세 명이 하단 탭 구조가 직관적이고 모바일 앱 형태라 처음 써도 쉽게 파악된다고 했습니다. 이건 유지했습니다.
두 명은 예상 문제 자동 생성이 가장 유용한 기능이라고 답했습니다.
대학 수업에는 문제집이 없어서 셀프 점검 도구로서 가치가 크다는 이야기였고, 이 기능도 그대로 유지했습니다.

개선 요청은 세 가지였습니다.
첫째로, "강의 등록"과 "노트 생성"이 어떻게 다른지 처음엔 헷갈린다는 의견이 있었습니다.
학기 초 1회 vs 매주 반복이라는 차이가 직관적으로 보이지 않는다는 건데,
Step 0 배지와 "학기 초 1회" 라벨을 UI에 추가해서 반영 완료했습니다.
둘째로, 다크모드에서 일부 화면의 색 대비가 약하다는 지적이 있었습니다.
전체 배경 CSS 변수를 재정의해 반영했습니다.
셋째로, 수업자료와 녹음 파일을 한 번에 여러 개 올리고 싶다는 의견이 있었습니다.
백엔드에 list 입력을 지원하고 프론트 UI도 추가해 반영했습니다.

5건의 피드백을 전원 반영하고 나서 만들어진 결과물이 바로 지금 보실 최종 빌드입니다.


[슬라이드 7 - 앱 시연 화면 소개] (1:00)

그러면 영상을 보시기 전에 전체 화면 흐름을 한눈에 먼저 보여드리겠습니다.

화면에 보이시는 것처럼, 왼쪽부터 온보딩, 회원가입 1단계, 회원가입 2단계, 로그인,
강의 등록, 노트 생성, 노트 조회, 노트 상세, 설정 화면 순서입니다.

온보딩에서 시작해 첫 노트 생성까지 끊김 없이 이어지는 흐름으로 UX를 구성했고,
모바일 앱 형태로 만들어서 처음 사용하는 분도 별도 설명 없이 바로 파악할 수 있습니다.
이 점이 외부 인터뷰에서 가장 먼저 나온 강점이기도 했습니다.

그럼 실제 안드로이드 기기에서 구동되는 시연 영상을 보여드리겠습니다.
영상은 약 3분입니다.

[슬라이드 9 - Gemini 직접 쓰면 되지 않나?] (1:30)

시연을 보고 나면 이런 생각이 드실 수 있습니다.
"어차피 Gemini 같은 AI 챗봇이 있는데, 그냥 직접 쓰면 되지 않나?"

저희도 그 질문을 개발 초기에 스스로에게 던졌습니다.
그리고 저희의 답은 네 가지입니다.

첫 번째, 원클릭 녹음 통합입니다.
지금은 별도 앱으로 녹음하고, 파일을 저장하고, 업로드하는 과정이 필요합니다.
로드맵에서는 앱 안에서 바로 녹음을 시작하고,
수업이 끝나면 생성 버튼 하나만 누르면 노트가 완성되는 흐름을 목표로 합니다.

두 번째, 강의계획서 기반 맥락 자동 주입입니다.
Gemini를 직접 쓰면 매번 "이 강의는 어떤 과목이고 교수님이 어떤 부분을 강조하는지"를
프롬프트에 직접 써야 합니다. 매주마다요.
저희 서비스는 학기 초 한 번 강의계획서를 등록해두면
그 이후 매주 자동으로 해당 맥락이 포함됩니다.

세 번째, 데이터 프라이버시 경로입니다.
현재는 Gemini로 STT를 처리하고 있지만,
Phase 2 로드맵에서는 음성이 저희 서버 안에서 Whisper로 처리되고
Gemini에는 텍스트만 전달됩니다.
음성 원본이 외부 서버로 나가지 않는 구조입니다.

네 번째, 한국 대학 시험 구조에 맞춘 최적화입니다.
일반 AI 요약은 내용을 정리하는 데 그치지만,
저희 노트는 교수님이 직접 강조한 힌트, 중요도 별점, 그리고 출제 경향 기반 예상 시험 문제까지 포함합니다.
단순 요약이 아닌 시험 대비 전용 노트입니다.


[슬라이드 10 - B2B 확장 · 수익화] (1:30)

여기서 한 발 더 나아가, 저희 파이프라인의 가능성을 말씀드리겠습니다.

저희 파이프라인의 본질은 강의 요약이 아닙니다.
"비정형 멀티모달 입력을 구조화된 출력으로 변환하는 AI 워크플로우"입니다.

이 구조에서 핵심은 Step 0 컨텍스트 문서만 교체하면 완전히 다른 도메인으로 전환된다는 점입니다.
코드는 전혀 건드리지 않아도 됩니다.
강의계획서 대신 회의 안건 목록을 넣으면 회의 요약 도구가 됩니다.
법무 검토 체크리스트를 넣으면 계약서 리스크 분석 도구가 되고,
사내 온보딩 가이드를 넣으면 신입사원 교육 정리 도구로 쓸 수 있습니다.

수익화 구조는 프리미엄 모델입니다.
무료 플랜은 강의 3개, 월 10회 노트 생성으로 서비스를 경험하게 하고,
Pro 플랜은 월 9,900원에 무제한 사용, 다중 파일 업로드, 노트 공유를 제공합니다.
Team 플랜은 월 29,900원으로 팀 단위 워크스페이스와 관리자 대시보드를 제공합니다.
현재 앱 화면에도 요금제 페이지가 구현되어 있습니다.


[슬라이드 11 - 최종 성과] (0:30)

한 학기 개발 결과물을 수치로 정리하면 이렇습니다.
API 엔드포인트 19개, 5단계 AI 파이프라인, 음성·PDF·필기 3종 입력 지원.
웹은 Railway에 배포 완료, Android APK·AAB 빌드 완료, Google Play 심사 진행 중,
외부 사용자 피드백 5건 전원 반영 완료입니다.


[슬라이드 12 - 기술 로드맵] (0:30)

현재 기술 스택이 단순한 이유는 몰라서가 아닙니다.
검증이 완료되기 전에 복잡도를 최소화하기 위한 의도적 선택입니다.

Phase 1인 지금은 SQLite와 단일 FastAPI, Railway로 가볍게 운영하며 실사용자를 확보합니다.
Phase 2에서는 PostgreSQL, S3, 이메일 인증으로 안정성을 보강하고,
Phase 3에서는 Celery·Redis 비동기 큐와 전용 Whisper STT 서버로 수십 명 이상의 동시 사용자를 처리합니다.


[슬라이드 13 - Google Play 현황] (0:30)

Android 패키징은 PWABuilder TWA 방식으로 진행했습니다.
APK와 AAB를 모두 빌드했고, 앱 ID는 com.cau.lecturenote입니다.
Google Play 비공개 테스트에 등록 신청을 완료했으며,
현재 구글의 검토 심사가 진행 중입니다.
승인이 나면 바로 비공개 테스트 배포가 가능한 상태입니다.


[슬라이드 14 - 마무리] (0:30)

저희가 이번 한 학기 동안 증명하려 한 것은 하나입니다.

우리가 직접 겪는 문제를, 가장 현실적인 기술로 해결한다.
